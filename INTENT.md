# OwnGo — INTENT

> Компілятор Go 1.27 без трасувального GC: незмінений Go-код, керування пам'яттю як у Rust.
> Основа — форк llgo.

## Мета

- **Вхід:** незмінений Go 1.27 — модулі, залежності, stdlib.
- **Вихід:** нативний бінарник без трасувального GC. Більшість об'єктів звільняється детерміновано в точці останнього використання.
- **Семантика:** програми поводяться так само, як зібрані `gc`. Специфікація Go не вимагає GC; змінюється лише час спрацювання `runtime.AddCleanup` і фіналізаторів.

## Не-цілі

- Гарантії borrow checker для незміненого коду: відсутність гонок даних не виводиться.
- Анотації чи новий синтаксис як вимога.
- Власні фронтенд, codegen чи рантайм з нуля.
- Rust у реалізації: OwnGo пишеться на Go, як llgo.
- Інтероп із C. cgo за замовчуванням вимкнено (`CGO_ENABLED=0`); частини llgo для C не використовуються і не видаляються.
- Інтероп із Python. Його видалено з компілятора, збирача й інструментів (2026-10-29) — свідомий виняток із принципу мінімального дифу з upstream.

## Обов'язкові принципи

1. **Незмінений код.** Програма, що збирається `gc` 1.27, збирається OwnGo без змін.
2. **Коректність понад економію.** Якщо володіння не доведено — слабша стратегія (RC, закріплення). Передчасний `free` неприпустимий.
3. **Кожен `free` перевіряється.** Debug-збірки — під ASan; тести — диференційні проти `gc`.
4. **Мінімальний диф з upstream llgo.** Зміни ізольовані: окремий пакет проходу і файли рантайму під тегом `owngo`. Регулярний rebase.
5. **Спершу виміри.** Кожна фаза починається з метрик і має гейт.
6. **YAGNI.**

## Модель пам'яті: каскад

| Рівень | Коли | Механізм |
| --- | --- | --- |
| 1. Стек | об'єкт не втікає | escape analysis `go/ssa` + наш прохід |
| 2. Статичне володіння | доведено єдиного власника і точку останнього використання | компілятор вставляє `free` |
| 3. Підрахунок посилань | усе інше | inc/dec з виведенням позичань (Perceus); атомарний за замовчуванням, неатомарний — якщо доведено, що об'єкт не покидає горутину |
| 4. Збирач циклів | лише цикличні типи, визначені статично за графом типів | trial deletion (як ORC у Nim) |
| Закріплення | `unsafe.Pointer` → `uintptr`, непрозорий `reflect`; cgo (лише якщо явно ввімкнено) — на час виклику | не звільняється; попередження компілятора |

Правила:

- `free` — у точці останнього використання: у Go немає деструкторів, чекати кінця області видимості не треба.
- `weak` і `runtime.AddCleanup` — через окремий лічильник слабких посилань.
- Регіони — відкладено до вимірів.
- Пакет `own` не потрібен. Пізніше, за потреби, — лише як твердження «тут статичне володіння без лічильників», інакше помилка компіляції.

## Архітектура

```
Go 1.27 ─▶ фронтенд llgo (go/packages + go/types + go/ssa)
        ─▶ прохід володіння (новий): стратегія для кожної heap-алокації,
           точки free / inc / dec
        ─▶ codegen llgo (LLVM): виклики runtime.Free і RC
        ─▶ рантайм (тег owngo): алокатор + Free + RC + збирач циклів
```

Точки вбудовування (перевірено по коду llgo):

- `cl/compile.go`: `*ssa.Alloc` з `v.Heap` → `b.AllocEx` — тут рішення про стратегію.
- `ssa/memory.go`: `allocTyped` → `runtime.AllocU` / `AllocZ` — тут виклики алокатора.
- `runtime/internal/runtime/z_nogc.go`: `AllocU` = `malloc` без звільнення — основа тегу `owngo`.

Алокатор:

- **Фаза 1:** `malloc` / `free` з режиму `nogc`; база об'єкта завжди відома.
- **Фаза 2:** алокатор з пошуком бази за внутрішнім указівником — BDWGC (`GC_base`, збирання вимкнено) або власний size-class. Рішення — за вимірами.

## Горутини

- **Фази 1–3:** модель llgo без змін — горутина = потік ОС (1:1), фіксований стек.
- **Трек M:N** — окремий від роботи з пам'яттю; стартує, якщо фаза 0 показує тисячі й більше одночасних горутин у сервісах. Для CLI і батч-програм не потрібен.
- **Стеки M:N:** фіксований розмір, зарезервований у віртуальній пам'яті; фізичні сторінки — при доступі. Стеки ніколи не переміщуються.
- **Точка вбудовування:** `runtime.NewProc` — бекенд сам вирішує, як виконати горутину.
- **Неатомарні лічильники** для об'єктів однієї горутини лишаються коректними: міграція між потоками лише в точках планування з бар'єрами пам'яті.
- **Кеші алокатора** в M:N прив'язані до логічного процесора (як P у Go), а не до потоку.

## Перевірка коректності

- **ASan** (LLVM) у debug-збірках: use-after-free, double free. У llgo інструментацію треба підключити.
- **Звіт про незвільнене** на виході програми: місце алокації і очікувана стратегія.
- **`_cmptest`:** вивід ідентичний `gc`.
- **`GOROOT/test`:** `xfail.yaml` не гірший за базовий llgo.

## Відкриті питання

- Поріг гейта фази 0.
- Алокатор фази 2: BDWGC без збирання чи власний size-class.
- `sync.Pool`: коли спорожнювати без циклів GC.
- Збирач циклів: тригер запуску (поріг кандидатів чи таймер).
- Escape analysis `go/ssa` грубіший за `gc`: власний прохід чи покращення в upstream llgo.
- Поріг кількості горутин для старту треку M:N.
- Розмір зарезервованого стеку горутини в M:N.

## Ризики

- Хибне виведення володіння = use-after-free. ASan і консервативний fallback обов'язкові.
- Атомарний RC може програти `gc` за пропускною здатністю.
- Розходження з upstream llgo; поведінкові відмінності llgo від `gc` (xfail).
- Пріоритети upstream llgo задає інтероп із C і Python; їхні рішення можуть не збігатися з потребами OwnGo.
- Модель 1:1 упирається в ліміти потоків (`ulimit -u`, `threads-max`, ліміт PID у подах Kubernetes) для сервісів з горутиною на з'єднання.
- `go/ssa` кладе в купу більше об'єктів, ніж `gc`, — прохід володіння має це компенсувати.
